# エンドエフェクタ事例データベース 設計メモ(既存の選定ツールとの比較と、足す → 複雑さを評価 → 簡素化 の記録)

## 1. 参照した既存の選定ツール(メーカーの「ハンドを選ぶ」道具)と、このツールが答える問いの違い
| ツール | 入口 | 出てくるもの | 使えるところ | 足りないところ(このツールが埋める) |
|---|---|---|---|---|
| SCHUNK Gripper Selection / Grip Assistant | ワークの寸法・重さ・材質・ロボットの型式 | 自社グリッパの型式とフィンガ | 条件 → 製品 の対応が精密 | 自社製品だけ。「世の中では何で掴むのが普通か」は分からない |
| Robotiq Application Guide / Lean Robotics | 用途(マシンテンディング・パレタイズ…) | 用途別の構成キットと事例 | 用途から入れる。事例に数字(台数・回収)がある | ワークの種類で横断できない。協働・UR 前提 |
| OnRobot Application Builder | 用途・ワーク・ロボット | 自社ハンド+ロボットの組合せ | ロボット横断 | 事例の画像が製品写真中心。他社・カスタムが無い |
| Schmalz Vacuum Gripper Configurator / Application videos | ワーク(材質・表面・重さ) | 吸着パッド・エリアグリッパの選定 | 吸着の可否の判断が速い | 吸着以外の選択肢が出ない |
| Piab piCOBOT / piSOFTGRIP の用途紹介 | ワーク(食品・箱・袋) | 自社製品 | 食品・袋物の実例が多い | 同上 |
| UR+ Marketplace | ハンドの製品一覧 | UR 対応製品 | 協働向けの製品が網羅 | 「どのワークに何が使われたか」の過去事例としては見られない |

共通点: どれも **製品を選ぶ** ための道具。このツールの問いは **「このワークはどう掴むのが一般的か。誰がどこでやったか」** で、答えは製品ではなく **実例の画像と、その掴み方の分布**。

## 2. 採用 / 不採用(LexxMoMa の商談に効くもの)
| 既存ツールの要素 | 判断 | 理由 |
|---|---|---|
| ワークの材質・重さ・寸法で絞る | **採用**(材質・重量帯。寸法は不採用) | 営業段階で分かるのは材質と重さまで。寸法で絞るほど件数が無い |
| 用途から入る(マシンテンディング…) | **採用**(作業の軸) | お客さまの言葉が用途から始まることが多い |
| ロボット型式で絞る | **一部採用**(産業用 / 協働 の 2 区分 + 移動マニピュレータ) | LexxMoMa は協働アーム + AMR。「協働でもできる?」が最初の問い |
| 製品の型式・価格・納期 | 不採用 | 製品 DB ではない。出典ページへ送る |
| 吸着の可否の計算(真空圧・パッド径) | 不採用 | エンドエフェクタ設計ツール(別ツール・開発中)の領域 |
| 事例の数字(台数・回収期間) | 不採用(本文は写さない) | 権利と本筋(掴み方)のため。要約は自分の言葉で、数字は出典へ |
| 自由文で聞く | **採用**(同義語辞書で分解 → チップ) | 「油の付いた鉄の丸棒を旋盤に入れたい」をそのまま入れられる。外部 API は使わない |
| 掴み方の分布 | **採用**(核となる機能) | 「段ボールは吸着 7 割」を一目で。1 件ずつ読まなくてよい |
| LexxMoMa での適用可能性 | **採用**(ただし「推測」と明記して事実と分ける) | 営業の次の一手につながる。根拠(可搬・形態)を列挙 |

## 3. データの設計で決めたこと
- 1 件 = 「あるワークを、あるハンドで、あるロボットで扱った実例」。同じ製品ページでもワークが違えば別の事例。
- 分類はすべて **語彙との一致** で付け、一致した語を `fieldSources` に残す(推測で埋めない)。LLM での補完は `method: inferred` の印を付けて区別する(初版では未使用)。
- 事例ではないページ(製品一覧・会社案内・業界紹介)は、ワークと掴み方の両方が付かない / 見出しに語が無く本文の一致が弱い、で落とす(`data/rejected.json` に理由を残す)。
- 同じ取得元の多くのページに同じ段落・同じ画像が出るなら定型文・バナーとして除く(安川のサイドバー「研磨・バリ取り…」、OnRobot の共通 og 画像で必要になった)。
- 画像は **縮小版だけ** を暗号化して置く(一覧 240px / 詳細 400px)。元画像・原本 HTML は `raw/`(gitignore)。

## 4. UI の改善の繰り返し(足す → 複雑さを評価 → 簡素化)

### 第 1 回(2026-10-26, パイロット 143 → 191 件)
足したもの:
- 自由入力 → 読み取りチップ(× で外せる) / ロボット区分のタブ / 移動マニピュレータの切替 / 並び替え(関連度・20 kg に近い順・新しい順)
- 「この条件での掴み方」: 大分類ごとの横棒 + 割合 + 代表画像 + 小分類の内訳。棒を押すと絞る
- 画像グリッド(縦横比を先に確保・遅延読み込み) / 詳細パネル(画像ギャラリー・出典とクレジット・事実と出典・推測の枠・似た事例・レビュー)
- 絞り込み(ワーク 2 階層・可搬重量帯(20 kg 以下に LexxMoMa の印)・掴み方 2 階層・作業・材料・種別・地域・業種・性質)
- 条件は URL の # に保持(🔗 でコピー)。スマホでは絞り込みを下からのシートに

複雑さの評価(1440px のスクリーンショットで確認):
- 1 画面目に 入力欄 → 傾向 → 画像 が収まり、問い → 答え の順になっている
- 絞り込みの軸が 9 本あり、左の列が長い。ただし件数 0 の選択肢は出さないので、実データでは 4〜5 本に収まることが多い
- 詳細パネルの「事実」は項目ごとに出典リンクが付くため行が多い。営業が見るのは画像・要約・推測の 3 つなので、その順に上から置いた

簡素化したもの:
- 傾向パネルの小分類の内訳は 3 つまで(スマホでは出さない)
- 絞り込みは 9 件を超えたら「あと N 件を見る」にたたむ
- カードの文字は 2 行の題名 + ピル(掴み方・区分・重量帯)+ 出典の 1 行だけ
- 遊び要素(ハンド図鑑)は入れていない。速さと本筋を優先し、利用が増えてから検討

速さ(Playwright, 143 件・画像 7.1 MB):
- ロック解除 → 最初の 24 枚: 0.74 秒(初回) / 0.52 秒(2 回目, Cache Storage)
- Fast 3G 相当: 初版は 8.8 秒(最初のパックが 700 KB で、2〜3 枚目の画像も入っていた)→ パックを 400 KB に分け、代表画像を先に詰める順に変えた
  → 一度 22.5 秒に悪化(残りのパックを同時に先読みして帯域を奪っていた)→ 最初の 24 枚のパックを順に取り、残りはその後に → 8.2 秒。目標 4 秒には届かない(データの復号 2.3 秒が残る)
- 絞り込み変更 → 画像がそろうまで 175 ms / 詳細の 400px 画像 71 ms(先読み済み)/ 外部ドメインへの画像リクエスト 0 件

次に直すもの(評価 7-3 の 3 役での指摘):
- 営業: 「TPポリ箱」で検索すると 0 件 → 条件を緩めて全件が出る。件数が無いワークは「まだ事例がありません」と伝えたうえで近い事例を出す方が分かりやすい
- アプリケーションエンジニア: 可搬重量が「不明」の事例が 6 割。ワークの重さが書かれていないページが多い。ハンド製品の可搬(例: Robotiq AX10 → 10 kg)から推定する規則を足す
- お客さま: 掴み方の名前(単パッド・フォーム吸着)が専門用語。傾向パネルは大分類(真空吸着・機械式…)で見せ、小分類は内訳として添える形にした

## 5. 分類の精度: 規則 → LLM レビュー の二段構え(フェーズ 2 ループ 6, 2026-10-26)
規則(語彙との一致)だけでは、本文に多くのワーク・用途が並ぶ事例ページを正しく読めない(抜き取りで分類の誤り 16〜20%)。規則を厳しくすると候補が 25% 減る(ループ 5)。
そこで役割を分けた:
- **規則** = 候補を広く集める(再現率)。事例らしさの判定は緩めに(見出しに語があるか、本文で 2 語以上か、3 点以上)
- **LLM レビュー**(Claude のサブエージェント、1 バッチ 40 件)= 公開する事例だけ本文を読んで確定する(適合率)。値は `method: inferred` + 本文の引用を `fieldSources` に残す

1 波目(369 件)の結果:
| 項目 | 件数 |
|---|---|
| 事例ではない(会社案内・製品一覧・溶接や研磨だけでハンドの把持が無い・SIer サイトの無関係ページ) | 211(57%) |
| 事例として確定 | 158 |
| うち規則と先頭のワークが違った | 94(規則は本文に並ぶ語を拾いすぎる) |
| うち規則と先頭の掴み方が違った | 35 |
| うちロボット区分が違った(規則が付けすぎ・付け足りず) | 15 |

判断: SIer サイトの自動発見(sier_discover.py)は無関係ページを多く拾う(2,281 ページ → 規則で 314 → レビュー後は 1/3 程度)。発見の段階で「ロボット」「ハンド」「把持」のいずれかが本文に無いページを候補から外す(次のループ)。
LLM レビューの費用は 1 件あたり約 3.5k トークン。2,000 件で約 7M トークン。公開する事例だけに限る運用でよい。

## 6. 画像の選び方の見直し(フェーズ 2 ループ 8, 2026-10-27)
抜き取りで「人物・縦長の帯・画面」が 12% 残っていた。公開中 575 枚を CLIP の点数で並べて目で確かめた:
| 点数の帯 | 枚数 | 中身 |
|---|---|---|
| 0.52〜0.66 | 81 | 73 枚が人物・サイドバーの縦長の帯・画面・工場の全景。ハンドの写真は 8 枚 |
| 0.66〜0.78 | 81 | 6 割がハンドの写真。人物(遠景・横向き)と帯が 2 割 |
| 0.78〜 | 413 | ほぼハンドの写真 |

直したこと:
- しきい値 0.52 → 0.62、縦長(h/w > 1.5)は使わない(帯と立ち姿だけだった)
- 点数が足りても「最も近い文」が悪い例(工場の全景・AMR だけ・人物)なら使わない(ラベルは判定済みで追加費用なし)
- 顔検出(OpenCV Haar)は **opencv 5 の wheel に分類器が同梱されず、ループ 1 からずっと 0 を返していた**。4.x に戻し分類器を crawler/models/ に置いた。ただし遠景・横向きの人物は検出できない(検出 0)ので、人物は CLIP の文に「人とロボットが一緒」「作業者が手で持つ」「集合写真」を足して弾く
- 文を変えたので判定済み 2,213 枚を再判定(rejudge.py、CPU 9 分)。しきい値は再判定後の点数で決め直す

結果(再判定後の点数で): しきい値 0.60 + 悪い例ラベルの除外で、公開中 575 枚のうち 165 枚を外し、うち目で確かめた 57 枚は 49 枚が人物・溶接・画面・閉じた工作機械だった(失うハンドの写真は 8 枚)。抜き取り 50 件の画像の誤りは 12% → 10%(人物+ロボットを許容しない数え方では 18%)。
残る誤りは「人がロボットの横に立つ写真」で、CLIP は 0.85〜0.94 でハンドの写真と判定し、Haar の顔検出(正面・横顔)も遠景では 0、HOG の人物検出も当たらなかった(良い写真に誤検出 3/24)。次の手は README の「次のセッションでやること」3 に。

## 7. 速さ: 最初の画面が遅かった本当の理由(ループ 8)
Fast 3G で 10.5 → 20 秒に悪化して調べた。画像の規則ではなく:
- 画像パックは追記式(Cache Storage を無駄にしないため)なので、事例の並びを変えても古い画像は古いパックに残り、最初の 24 枚が 4〜5 パックに散っていた → `build.py --repack` でパックを UI の並びで作り直す(並びの式も search.js の score() と同じに)
- 傾向パネルの代表画像 7 枚が別のパックを同時に引いていた → 最初の画面のパックが届いてから取る
- Web フォント(Noto Sans JP: CSS 340 KB + 字形 42 本 = 1.4 MB)が画像と帯域を取り合っていた → 最初の画面の後に読む(それまで system-ui)
結果: Fast 3G 4.1 秒(内訳: データ 317 KB + 鍵導出 1.8 秒、最初のパック 405 KB 2.3 秒)。通常回線 0.31 秒。

## 8. 別の環境での再開と、レビューで見つかった規則の誤り(フェーズ 2 ループ 9, 2026-10-28)
作業データ(data/・raw/ 約 84 MB + 原本 1.8 GB)は gitignore なので、環境が変わると消える。アーカイブを渡す手が無いときの復元手順を決めた:
- 公開側の暗号化データには、事例ごとの出典 URL と LLM レビュー済みの値(method: inferred、本文の引用)が入っている。`recover.py` で復号して 候補 URL・取得元(search:/sier: のキー)・レビュー結果 を data/ に戻し、原本と画像だけ取り直す(2 秒間隔で約 1 時間)。258 件中 252 件が同じ値で戻った(残りは取得エラーと画像の取り直しで失敗)
- 戻せないもの: 「事例ではない」と判定した 236 件の記録、画像の CLIP 判定(取り直せば同じ)、検索で見つけたが未採用の URL。前者は同じページが再び候補に入ればレビューし直すだけ(費用は 1 件 3.5k トークン)
- 検索エージェント向けの手順(search_brief.md)は data/ に置いていたので消えた → crawler/ に置いて Git 管理に

LLM レビュー 335 件(10 バッチ)の報告から、規則の系統的な誤りが 3 つ見つかった(抜き取りでは見えなかった種類):
| 誤り | 原因 | 直し方 |
|---|---|---|
| ワークの重さの大半がロボットの可搬重量・本体重量・把持力 | `workpiece_mass` の文脈語に「payload / 可搬」が入っていた(ロボットの仕様表の数字を拾う) | 可搬・本体重量・把持力・リーチの語が近くにある数値は使わない。レビューが「本文に無い」と判断した重さは消し、可搬帯はロボットの可搬から引き直す(llm_merge) |
| Robotiq「Palletizing Solution」が Comau・MWES・Photoneo の事例に付き、掴み方が multi_pad に、さらに重複判定(メーカー+型式+ワーク+用途)で 26 件が 1 件に束ねられた | ee_products のパターンが `Palletizing Solution` だけで一致していた。重複判定の製品キーは顧客を区別しない | パターンは Robotiq の語が近くにあるときだけ。製品キーで束ねるのは題名の固有名詞(顧客名)も共通のときだけ(dedupe.py) |
| 韓国の事例ページで、別の事例のロボット型式・ワークが付く(川崎 RS007 が UR5e の事例に) | ページ末尾の「추천 도입사례」(推薦事例)の見出しと本文を本文として取り込んでいた | 関連記事の節の除外語に 추천・관련・相关案例・推荐 を追加(extract.py)。抽出をやり直すと語が減って規則の足切りに掛かるので、レビューで事例と確定した id は足切りしない(classify.py の lenient) |

語彙の抜け(なぜ漏れたか: 語彙): 마로솔 myrobotsolution.com の事例 466 本のうち 453 本が「カテゴリ 0 / 掴み方 0」で落ちていた。韓国語の同義語 77 組とロボット区分・移動の語、Rainbow Robotics・Neuromeka の型式を足して 126 本が通過、レビュー後 86 件。中国語(ループ 5)と同じ形で synonyms.yaml に節を置く。

速さ: 件数 258 → 403 で data.enc が 318 → 448 KB になり Fast 3G が 4.1 → 5.7 秒に。公開側には UI が使わない値(規則の点数 quality.scores、レビューの note)を入れないようにして 352 KB・4.2 秒。平文の data/cases.json には残す(確認用)。

## 10. 取りこぼしの調査: 規則が「掴み方 0」で捨てていた事例(フェーズ 2 ループ 10c, 2026-10-29)
分類で落ちた 7,300 ページを「落ちた理由 × 取得元」で集計すると、メーカーの事例一覧(UR・KUKA・FANUC・Yaskawa・Mech-Mind・마로솔)が「ワークは当たるが掴み方 0」で大量に落ちていた。
これらの事例は「ロボットが部品を取り出してコンベヤに置く」とだけ書き、ハンドの種類を書かない。規則は掴み方が 1 つも当たらないと LLM レビューの前に捨てていた(ループ 6 で「規則は広く集め、精度はレビューで」と決めたのに、ここだけ狭いままだった)。
直し方: ワーク・扱う作業(取り出し・パレタイズ・機械への投入など。溶接・研磨・検査だけは除く)・ロボットの語がそろえば「記載なし(写真で確認)」で残す。逆に掴み方はあるがワークの語が無いものは「汎用」で残す。2,728 ページ中 2,191 ページが規則を通り、画像の確認後 1,442 件をレビュー、約 940 件が事例と確定した(採用率 65%: 検索の 2 割より高い)。
複雑さの評価: classify.py に条件 2 つと定数 2 つ。代わりに「記載なし」が 59% になり、掴み方の傾向パネルの情報量が下がった(次の手は写真からの判定。ユーザーと相談)。
重複判定: ロボットダイジェストの同じ記事が一覧のタグ(&r=)と連載(&ca=5)の 2 つの URL で入り 21 件重複していた。url_id は変えず(作業データの id が変わるので)、重複判定のときだけ一覧用のクエリを無視する(dedupe.url_key)。
画像の悪い例ラベルを足す試み(ループ 10d、取り下げ): 抜き取りの誤り(コンベヤだけ・機械の外観・看板・製品の山・カメラ製品)を CLIP の悪い例に 5 文足して全 13,784 枚を再判定した(CPU 64 分)。
公開中 3,140 枚のうち 381 枚が外れる計算だったが、40 枚を目で見ると半分以上がハンドの製品写真・ハンドの CAD・ハンドの付いたロボットだった。文を足すと softmax の分母が増えて良い画像の点数も 0.60 を割る。誤りを減らす代わりに良い画像を同じくらい失うので取り下げ、文の集合はループ 8 のまま(誤り 14%)。次に試すなら、文を足すのではなく「点数 0.60〜0.70 の帯だけ別の判定(人の目か別のモデル)」。
動画の静止画(ループ 10d): Bigwave(us.bigwaverobotics.com)の事例 94 件は、画像がすべて YouTube の動画サムネイルだった。動画の静止画は使わない方針(権利の整理が要る)なので、images.py で ytimg.com・vimeocdn.com・hqdefault.jpg などの URL を画像の候補から外す(images.VIDEO_THUMB)。
URL で分からない「再生ボタンを描き込んだ画像」「文字だけのバナー」は CLIP が 0.60 を超えることがある。抜き取り(spot_sheet.py)で見つけたら manual/suppressions.json に画像単位で足し(delete_case.py --image)、画像が無くなった事例は build.py が載せない。

## 11. 写真から掴み方を判定する(フェーズ 2 ループ 11, 2026-10-29)
本文に掴み方の記載が無い事例が 1,208 件(60%)あり、掴み方の傾向パネルが弱かった。写真に写ったハンドの形から方式を付ける。
- 画像認識: 写真を読めるモデル(サブエージェント)が、15 事例ずつの番号付きシートを見て大分類・小分類・確からしさ(high / medium / low)と「見えたもの」を書く。写っていなければ unknown(場面からの推測はしない: パレタイズ = 吸着とは限らない)。
  一次で medium(ハンドが小さい)だった 645 件は、元画像から 460×345 で切り出した 6 事例ずつのシートで二次判定。
- パターン認識: CLIP(ViT-B/32)の画像特徴に線形分類器(多クラスのロジスティック回帰、群の件数で重み)を学習。教師は本文から掴み方が分かっている 742 件。単独の正解率は 5 分類で 52% と低い(写真の大半は工場の場面で、ハンドは小さい)。ViT-L/14 は CPU で 1 時間以上かかるので使わなかった。
- 合議: 一次 high / 二次 high / 二次 medium が一次と同じで CLIP の最上位とも一致、のどれかだけを反映する。CLIP が一致すると視覚判定の精度が上がる(一次 high で 94%、不一致だと 62%)。
- 測り方: 正解の分かっている事例をシート 1 枚に 3 件ずつ伏せて混ぜた(判定するモデルにはどれか分からない)。本文との一致は 80%。不一致を目で裁定すると、本文側の誤り(SRT の蛇腹吸盤が本文の語で「ソフトフィンガ」)が多く、写真側の誤りは写ったカメラ・溶接トーチを作業ツールとしたもの(4 件)と、膨張式・ソフトの把持を吸盤と見たもの(2 件)。作業ツールは写真からは付けない。
- 表示と記録: fieldSources の method を "photo"(evidence は見えたもの)、end_effector.by_photo を一覧用データに。小分類が写真で決まらないものは語彙の mech_photo / vacuum_photo(photo_only: 本文の語・LLM レビューでは使わない)。
  本文や LLM レビューが掴み方を付けた事例は書き換えない。recover.py は写真から付けた掴み方をレビュー結果に混ぜず data/photo_grasp/results.json に戻す。
- 判定したモデルの 1 体が、画像が読めないまま 4 枚分を書いていた(本人の報告で分かった)。その 4 枚は捨ててやり直した。指示に「画像が読めなければ書かない」を入れた。
- 結果: 記載なし 60% → 49%。残る 972 件は写真にハンドが写っていない。
